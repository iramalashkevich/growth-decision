# A/B-тесты: дизайн, проведение, чтение результата

Открывай этот файл, когда вопрос про эксперимент: спланировать, посчитать трафик, оценить результат, решить «раскатывать или нет». Считай через `scripts/ab_calc.py` — не оценивай размер выборки на глаз.

---

## 1. Гипотеза: 4 обязательных компонента

Гипотеза без любого из них не допускается к тесту (практика Flo, давшая +30% успешных экспериментов):

1. **Изменение** — что именно меняем, с мокапом/скетчем. «Улучшим онбординг» — не изменение.
2. **Сегмент** — на кого действует, в терминах Segment+Job. Кому опыт реально поменяется.
3. **Метрика** — целевая (одна!) + guardrail/health-метрики.
4. **Масштаб эффекта** — ожидаемое изменение в %, обоснованное данными или исследованием, а не «должно вырасти».

Плюс пятый, без которого гипотеза нефальсифицируема: **механизм** — почему это должно сработать (какой барьер Job снимается). Без механизма результат нечему научить: и успех, и провал будут необъяснимы.

**Шаблон:**
> Для `<сегмент + Core Job>`, если мы `<изменение>`, то `<целевая метрика>` вырастет на `<X%>` за `<срок>`, потому что `<механизм: какой барьер снимается>`.
> Подтверждено, если `<критерий>`. Опровергнуто, если `<критерий>`. Guardrail не должен упасть ниже `<порог>`.

**Отбор гипотез — Data-Informed ICE:** Impact (решает ли реальную проблему сегмента) × Confidence (есть ли подтверждение в данных/ресёрче) × Ease (сложность реализации). «Data-informed» означает: аналитик даёт прогноз влияния, но оценку каждый ставит сам — иначе ICE вырождается в защиту любимой фичи.

## 2. Дизайн: что фиксируем ДО старта

Незафиксированный дизайн = невалидный результат. Заполняй `assets/experiment-design-template.md`.

| Параметр | Комментарий |
|---|---|
| Целевая метрика | Ровно одна. Остальные — вторичные/guardrail |
| Guardrail / health-метрики | Что не должно сломаться: crash rate, скорость, отписки, саппорт-тикеты, retention |
| Прокси-метрика | Если целевая долгая (retention D30, LTV) — заранее договориться о прокси и о том, что она валидирована на истории |
| Baseline | Текущее значение метрики |
| MDE | Минимально значимый эффект — **бизнесово** минимальный, ниже которого раскатывать не будем |
| α (уровень значимости) | Обычно 0.05 |
| Мощность (1−β) | Обычно 0.8, для дорогих решений 0.9 |
| Односторонний/двусторонний | По умолчанию двусторонний |
| Размер выборки на группу (n) | Считается, не угадывается |
| Длительность | ≥ полного цикла активности пользователя, целое число недель |
| Единица рандомизации | user / device / session / город — должна совпадать с единицей анализа |
| Кто попадает в тест | Только те, чей опыт может измениться (см. §5) |
| Действия при каждом исходе | Что делаем если +, если −, если нет эффекта |

**Формулы (реализованы в `ab_calc.py`):**

Для конверсий, на группу:
```
n = ( z_{1-α/2}·√(2·p̄·(1−p̄)) + z_{1-β}·√(p₁(1−p₁)+p₂(1−p₂)) )² / MDE_abs²
где p₁ = baseline, p₂ = p₁ + MDE_abs, p̄ = (p₁+p₂)/2
```
Для средних (ARPU, чек, число действий):
```
n = 2·(z_{1-α/2} + z_{1-β})²·σ² / MDE_abs²
```
Длительность:
```
дни = 2·n / (число подходящих пользователей в день)   # 2·n, потому что две группы
```
Ключевое свойство: **n растёт как 1/MDE²**. Хотите ловить эффект вдвое меньше — нужно вчетверо больше трафика. Отсюда практическое правило: если требуемый n недостижим, менять надо не тест, а гипотезу — на такую, у которой ожидаемый эффект крупнее.

Онлайн-калькуляторы для перекрёстной проверки: [Evan Miller](https://www.evanmiller.org/ab-testing/), [SurveyMonkey](https://www.surveymonkey.com/mp/ab-testing-significance-calculator/), [Яндекс](https://yandex.ru/adv/statvalue).

## 3. Проблема подглядывания (peeking) — главная причина ложных «побед»

Классические критерии (z, χ², Стьюдент) валидны только при **заранее зафиксированном** размере выборки. Если смотреть на промежуточные результаты и быть готовым остановить тест при первом пересечении порога значимости, фактический уровень ошибки I рода растёт:

| Число подглядываний с готовностью остановиться | Во сколько раз занижен реальный p-value |
|---|---|
| 2 | ×2 |
| 5 | ×3.2 |
| 10 000 (автоскрипт каждый час) | >×12 |

Причина: даже у двух **идентичных** групп разница метрик случайно колеблется и периодически выходит за границы доверительного интервала. Останавливая тест ровно в этот момент, вы систематически собираете шум.

**Что делать:**
- Заранее рассчитать выборку → собрать данные → проверить результат один раз.
- Смотреть на динамику можно, **принимать решение — нет**. Устойчивая значимая разница, держащаяся несколько дней, надёжнее одноразового пересечения порога.
- Нужно легально подглядывать → используй методы, спроектированные под это: **sequential testing** (mSPRT), **alpha spending** (O'Brien–Fleming), **байесовский подход**. Обычный z-тест сюда не годится.
- Автоматические алерты «тест выиграл» без фиксированного горизонта — источник ложноположительных, а не ускорения.

## 4. Другие виды тестов

- **A/A** — обе группы получают одинаковую версию. Проверка инфраструктуры сплитования: если A/A регулярно даёт «значимые» различия, вся ваша система тестов врёт. Запускать при внедрении платформы и после её изменений.
- **A/A/B** — две контрольные + одна тестовая: валидирует систему прямо внутри боевого теста.
- **Switchback** — версии чередуются во времени/по локациям. Обязателен там, где есть **сетевые эффекты и общий пул ресурсов**: маркетплейсы, такси, доставка, соцфичи. Обычный user-split там ломается, потому что группы влияют друг на друга (спилловер).
- **MVT (многофакторный)** — несколько элементов сразу, чтобы найти лучшую комбинацию. Требует кратно большего трафика; для большинства команд это ловушка — лучше последовательные A/B.
- **Ухудшающий тест** — см. §6.
- **Holdout / geo-lift** — когда рандомизация по пользователю невозможна (бренд-медиа, ТВ, офлайн): контрольные гео/группы, не получающие воздействия.

## 5. Как ускорить тест, ничего не сломав (экспозиция)

Самая частая причина «нам не хватает трафика» — в тест засунули **всех активных пользователей**, хотя опыт меняется у меньшинства. Остальные добавляют только шум и разбавляют эффект.

Два приёма:

1. **Экспонировать только тех, чей опыт может измениться** — включать пользователя в эксперимент в момент триггера. Тестируем пуш о брошенной корзине → в тест попадают те, кто **бросил корзину**, в момент, когда бросил, а не все активные.
2. **Считать метрики с момента экспозиции конкретного пользователя**, а не с даты старта эксперимента. Предэкспериментальные данные не отражают влияние изменения и только зашумляют.

Эффект от смены методологии в реальном кейсе: результат перешёл из незначимого (p-value 28%) в значимый прирост конверсии **+2.7%** — на тех же данных, просто за счёт корректной экспозиции. Сигнал ловится в разы быстрее.

Другие легальные ускорители: CUPED (использование предэкспериментальных данных для снижения дисперсии), выбор менее шумной/более чувствительной метрики, прокси-метрики вместо долгих, увеличение доли трафика в тесте.

## 6. Ухудшающие тесты — самый недооценённый инструмент

Идея: вместо дорогого улучшения намеренно **ухудшить** фактор для части пользователей и измерить эффект. Дёшево, быстро, и отвечает на вопрос «а это вообще рычаг?» до инвестиций.

Как: отключить/ухудшить функцию для части аудитории на ограниченный срок → замерить метрики → оценить зависимость → экстраполировать, сколько дало бы улучшение.

Примеры: замедлить приложение на 1–3 сек и посмотреть на retention/конверсию; отключить пуши части аудитории; убрать поиск в каталоге; разные сроки ответа саппорта.

Когда применять: **до** того, как собирать выделенную команду или запускать крупный проект под улучшение фактора. Ухудшающий тест превращает корреляцию («быстрые сессии лучше конвертят») в проверенную причинность и даёт порядок величины рычага. Этика/риск: ограниченная доля трафика, короткий срок, guardrail на жалобы и отток, никаких ухудшений в критичных для безопасности/денег местах.

## 7. Ловушки, из-за которых результат недействителен

| Ловушка | Что происходит | Что делать |
|---|---|---|
| **Преждевременная остановка** | ложноположительный результат (см. §3) | фиксировать n заранее либо использовать sequential/Bayes |
| **Нет чёткой гипотезы** | нечего опровергать, любой исход «объясняется» | 4+1 компонента из §1 |
| **Novelty / primacy effect** | всплеск от новизны принимается за устойчивый рост; или наоборот — привычные пользователи временно проседают | смотреть динамику эффекта по неделям, тестировать на новых пользователях отдельно |
| **Множественные сравнения / p-hacking** | десятки метрик и сегментов → «значимость» найдётся случайно | заранее одна целевая метрика; Bonferroni/FDR для остальных; сегментные находки = только новые гипотезы, не выводы |
| **SRM (перекос групп)** | соотношение не 50/50, пользователь попал в обе версии | проверять SRM до анализа (`ab_calc.py srm`); жёстко фиксировать пользователя к варианту |
| **Сезонность и внешние события** | праздники, распродажи, кампании, релизы | целое число недель, ведение календаря событий, не тестировать в аномальные периоды |
| **Спилловер / сетевые эффекты** | группы влияют друг на друга | switchback или гео-сплит |
| **Несовпадение единиц** | рандомизация по пользователю, анализ по сессиям | единица анализа = единица рандомизации |
| **Выжившие / логирование** | часть событий не долетает в одном из вариантов | A/A и sanity-check объёмов событий |
| **Статзначимо ≠ важно** | при большом n значимым становится +0.1% | сверять с MDE и экономикой; смотреть доверительный интервал, а не только p-value |

## 8. Как читать результат

- **Смотри на доверительный интервал эффекта**, а не только на p-value. CI = [−1%; +9%] означает «мы ничего толком не узнали», даже если точечная оценка +4%.
- **p-value — это не** вероятность того, что B лучше A, и не размер эффекта. Это вероятность увидеть такую или большую разницу при условии, что разницы нет.
- **«Не значимо» ≠ «эффекта нет».** Проверь, была ли у теста мощность поймать эффект размера MDE. Если нет — вывод «не измерили».
- **Практическая значимость:** эффект ниже MDE, ради которого затевались, — это отрицательный результат, даже при p<0.05.
- **Guardrail-метрики** проверяются всегда, даже при победе целевой.
- **Сегментный разрез** — генератор гипотез для следующего теста, а не основание для раскатки на сегмент.

**Решения после теста** (все шесть — легитимные исходы):
1. Раскатать на 100%.
2. Раскатать частично (на сегмент, где эффект подтверждён отдельным тестом).
3. Докрутить и перезапустить — если механизм подтвердился, а исполнение слабое.
4. Отказаться и зафиксировать знание (что именно опровергнуто — это ценность, а не провал).
5. Повторить тест — если были нарушения дизайна или пограничный результат.
6. Разобрать побочные эффекты — целевая выросла, guardrail упал: разобраться до раскатки.

Каждый исход фиксируется в базе экспериментов: гипотеза, механизм, дизайн, результат, решение. Иначе команда будет заново тестировать одно и то же раз в год.
